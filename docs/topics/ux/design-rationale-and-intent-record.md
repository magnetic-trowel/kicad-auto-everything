# Design rationale and the intent record ("the why")

Scope: design-rationale literature, intent-capture mechanisms in 2026 EDA agents, and the intent sidecar design for our system. Not here: intent IR schema -> [../architecture/constraint-ir.md](../architecture/constraint-ir.md); relation vs coordinate interfaces -> [../llm/interfaces-relations-vs-coordinates.md](../llm/interfaces-relations-vs-coordinates.md).
Keys: design rationale, intent record, intent sidecar, `board.intent.json`, IBIS, QOC, ADR, Karsenty 41%, LLM rationale precision 0.27 recall 0.63–0.72, RAC, Who Plans, design as code, provenance tags, audit trail, ledger, lineage log, residual risk

## Rationale literature

| Work | Finding | Source |
|---|---|---|
| Karsenty (CHI '96) | Captured rationale answered only 41% of six professional designers' questions about a past design | [ACM](https://dl.acm.org/doi/fullHtml/10.1145/238386.238462) [S] |
| IBIS / QOC (gIBIS 15 years on) | Capture overhead and interruption of flow; early successes didn't scale; retrieval from large, decontextualized argument records is hard | [S] |
| LLM-generated design rationale (ACM TOSEM 2025) | 100 architecture problems, 5 LLMs: precision 0.267–0.278, recall 0.627–0.715. Of arguments experts didn't mention, 64.45–69.42% helpful, 1.59–3.24% potentially misleading | [2504.20781](https://arxiv.org/abs/2504.20781) [P] |
| ADR generation | Naming "Architectural Decision Record" in the prompt improved zero-shot output, still below human level | [2403.01709](https://arxiv.org/pdf/2403.01709) [S] |

Classic capture failed on capture effort and retrieval; logging structured rationale at decision time, anchored to board objects, removes both barriers [I].

## Intent-capture mechanisms in EDA systems

2026 systems converge on four mechanisms [P]: checkable named relations (RAC); structured diagnoses (evidence, hypothesis, falsifier); audit trails (stored prompts, ledgers, lineage); design as version-controlled, deterministically regenerated code.

| Mechanism | Evidence | Source |
|---|---|---|
| Intent as checkable relations | RAC's agent "decides which relations an artifact should satisfy"; failures return as "semantic repair evidence, so repair operates on intent instead of geometry"; checker independent of the solver | [2610.20935](https://arxiv.org/abs/2610.20935) [P] |
| Structured diagnosis and audit | "Who Plans": evidence, hypothesis, falsifier; intents with target, mechanism, operators, scope, expected effect. "Every repair-model prompt is stored before the call". Per-role ledger (tokens, spend, tool time); evidence builder attributes degradation to parasitic groups | [2610.24234](https://arxiv.org/abs/2610.24234) [P] |
| Design as code | "The design exists entirely as version-controlled code and regenerates deterministically"; human reviewers as gates with machine-checkable criteria | [2608.31006](https://arxiv.org/abs/2608.31006) [P] |
| Explanations for congestion | MLLMA: MLLM-guided genetic prompting + interpretable preference learning → "Design Suggestion Deck" of influential features and fixes; SOTA on CircuitNet | [2510.15872](https://arxiv.org/abs/2510.15872) [P] |
| Explained parameters | HyperPlace "proposes and explains hyperparameter configurations" | [2606.19795](https://arxiv.org/abs/2606.19795) [S, via survey] |
| Mechanism memory | GoalEvolve keeps "local effects, optimization debt, and downstream retention" as evidence | [2608.16733](https://arxiv.org/abs/2608.16733) [P] |
| Handoff provenance | "Residual risk [should] accompany accepted handoffs"; artifacts "traceable, auditable, and reusable". LayoutCopilot keeps "the request, command history, and rejected alternatives for designer review" | [2606.19795](https://arxiv.org/abs/2606.19795) [P] |
| Reviewable diffs | AlphaEvolve: changes "directly in Verilog… foster trust and simplify adoption" | [2506.13131](https://arxiv.org/abs/2506.13131) [P] |
| Provenance KGs | Datasheet facts kept with source provenance | [2610.12762](https://arxiv.org/abs/2610.12762) [P] |
| Lineage logs and journals | CoEvoP&R logs config, program, prompt, response, metrics, "sufficient to reconstruct candidate lineage"; ICPI keeps a design journal in an act–observe–reflect loop | [repo](https://github.com/FCHXWH823/CoEvoP-R); [2608.13767](https://arxiv.org/abs/2608.13767) [P/S] |

## PCB-specific need

- Diode: review is "reconstructing the intent of the engineer"; "intent lives outside the file" ([Diode](https://blog.diode.computer/hardware-review)) [V].
- DeepPCB on RL: "can't articulate the underlying principle" [V].
- Reuse: you must work out "which layout decisions mattered" when reusing reference circuits (KiCad forum) [S].
- StationX: "keep the AI's inferences labelled as inferences, or the workflow starts laundering guesses into 'facts'" [P, anecdote].

## Intent sidecar design [I]

The committed relation bundle *is* the intent record; explanations are generated by walking its links, not composed afterwards.

1. Sidecar next to `.kicad_pcb` (e.g. `board.intent.json`; schema owned by [../architecture/constraint-ir.md](../architecture/constraint-ir.md)). Per relation: the relation; its source (datasheet KG node and page, user requirement, recipe, or corpus prior); the planner diagnosis that introduced it; checker verdict and measured margin; accepted / rejected / relaxed status and who decided.
2. Explanations walk these links. "Why is C12 here?" → relation `near(C12, U3.VIN, tight)`, sourced from TPS62933 p.X ("as close as possible") plus the corpus prior, realized margin (2.3 mm), measured loop area.
3. Object-anchored rationale log (IBIS/QOC-lite): issue, options considered, criteria, choice, evidence; attached to affected parts, nets or zones; captured automatically at action time; searchable; survives edits; exportable as a design-review document (CC-BY-4.0 docs).
4. Provenance tag on every claim: measured / rule / datasheet / estimate / inference. LLM-drafted rationale never shown untagged (precision ~0.27).
5. Store prompts before calls; per-role ledger and lineage logs for reproducibility.
6. Residual-risk list at each handoff: what was not checked, what was assumed.
7. Design as code where possible: board regenerates deterministically from intent + solver version + seeds.
8. The relation bundle re-solves after ECOs and resizes without LLM calls (RAC: 89.5% vs 65.6%), so intent persists through change.

## Open questions

- No standard PCB design-intent schema; no user study of whether engineers trust LLM layout explanations.
- How to record non-checkable preferences (aesthetics)? Possibly house-style preference records learned from edits.
