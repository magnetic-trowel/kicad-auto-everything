# kaeq: job queue for a shared machine

A single stdlib-Python file. Many Claude sessions submit shell commands; one daemon
starts them as room appears and tells the *submitting* session what broke.

## Setup (once, on the host)

```bash
tools/kaeq/install.sh          # symlinks ~/.local/bin/kaeq, prints `kaeq doctor`
kaeq install-service           # optional: systemd --user unit; then `loginctl enable-linger $USER`
```

The daemon auto-starts on the first `kaeq submit`, so the service is only for reboots.
Sessions on other machines: `export KAEQ_SSH=<host>`; every `kaeq ...` then runs over ssh
(paths are host paths, so the repo must be checked out on the host).
To stop permission prompts, allow one rule in each session's settings:
`"permissions": {"allow": ["Bash(kaeq:*)"]}`. Sessions load the usage text from
`~/.claude/skills/kaeq/` (installed by `install.sh`, so every repo gets it).

## How it shares the machine

| Concern | Mechanism (all unprivileged, Ubuntu 22.04) |
|---|---|
| Other users' CPU | Jobs run at nice 19 and `SCHED_IDLE` (inherited by children; the daemon itself runs at nice 10, above its jobs and below normal work): they only get cycles no normal-priority task wants. Jobs are pinned to `threads - reserve_cpu` CPUs (`cpu_affinity=auto`), a hard cap that needs no cgroup `cpuset` (often not delegated to user slices). Admission also counts other users' measured load, so `reserve_cpu` threads stay free beyond it. A job's CPU use is read from its scope's `cpu.stat` (which includes children that already exited), and no job starts while the machine's ready-to-run threads (`procs_running`, smoothed) plus its `--cpus` exceed `threads - reserve_cpu`: past that point more work only slows every running job. |
| Job classes (`--class`, `kaeq class`; default `default_class`, batch) | **timed**: for timing, benchmark, optimization and speed work (kaeres experiment runs), anything whose results depend on the time it gets (benchmark attempts, anytime methods, DRC, physics with a zone refill). Never frozen or throttled (`memory.high` max), so no clock inside it runs while it is stopped; its unused grant counts as taken (`timed_hold_frac`, 1); it gets memory before batch jobs, and if none is free, the newest batch job (a frozen one first) is requeued to make room, at most every `timed_preempt_s` (30 s). Runs at nice `timed_nice` (10), far above batch jobs (`SCHED_IDLE`), which only get the cycles timed jobs leave. **batch** (the default): everything else: the elastic memory leases below, may be frozen (and compressed) for memory or CPU; a wall-clock limit inside a batch job can trip during a freeze. Like Kubernetes' Guaranteed and Burstable classes. |
| Memory for timed jobs (forecast, `timed_forecast`) | A timed job is never paused, so if memory runs short the only result-safe action is to requeue a job (it restarts from scratch). Collisions are kept rare by forecast instead of reservation: each job past `lease_warm_s` may reach its expected size (`--mem` × its owner's **median** peak/`--mem` × `mem_learn_margin` (1.1), from `mem_learn_min_jobs` (20) finished jobs, not capped at `--mem`; or the most it has used), and spends its life at each fraction of that as its owner's finished jobs did (their memory histograms), jobs of one owner correlated as measured; mean + `timed_z` std of that growth, pooled over all timed jobs, is set aside (`pooled_headroom`). The median keeps a few badly under-declared jobs from sizing every job of their owner. `timed_z` (2) adapts every `overcommit_every_s` (10 min) to the work lost to requeues over `overcommit_window_s` (6 h): above `overcommit_loss_target` (2%) of the timed work done +0.5, below half of it -0.25. Below half the growth buffer (`lease_buffer_ticks` × the fleet's largest net growth in a tick), the job losing the least work per MB freed is requeued (`evict_every_s`; spared after `evict_protect_after` (2) requeues). |
| Squeezing running timed jobs (`squeeze`) | When free memory beyond the reserve falls below the growth buffer (requeues start only at half of it), the biggest running timed job (preferring one not growing fast) has up to twice the shortfall (at most half its memory) compressed into zram while it keeps running: its scope may swap for a moment and `memory.reclaim` takes its oldest pages (MGLRU), then swapping is off again. It pays a few µs only when it touches a squeezed page; a job that pulls back (`workingset_refault_anon`) over a quarter of what was squeezed out of it is hot and not squeezed again. Squeezed pages count as used, not as room it will grow back into. One squeeze at a time, at most every `squeeze_every_s` (5 s), in 512 MB steps that pause while the user manager's memory pressure is above 10%. Recorded per job (`squeezed_mb`; `kaeq usage` SQUEEZED_GB). Order on a shortage: freeze and compress batch jobs, squeeze timed jobs, requeue the cheapest job last. Admission counts `squeeze_credit` (25%) of timed jobs' memory (past warm-up, running, not hot) × (1 − 1/`zram_ratio` (1.4)), capped by zram room, as extra room: the queue runs into shortages on purpose and squeezes to cover them. |
| Compressing frozen jobs (`compress_frozen`) | A frozen job is compressed: its scope may swap (`memory.swap.max`) and its memory is reclaimed (`memory.reclaim`) into zram swap only (`zram`, default; `any` also uses disk swap, for tests; `off`), so a freeze frees RAM. While a compressed job is frozen nothing new starts; it gets memory first, and is thawed only when there is room for what it has in swap; after the thaw what is still in swap stays set aside and swapping is off again. Needs a zram swap device, which only root can create (once): e.g. `zram-generator` with `zram-size = ram / 4` and `compression-algorithm = zstd`, or `modprobe zram; zramctl -f -s 64G -a zstd; mkswap; swapon -p 100`. Measured on physics evaluations, their memory compresses about 1.3-2x. |
| Keeping expensive jobs running (`keep_gb`, `keep_core_h`, `thaw_min_run_s`, `heavy_boost`) | A frozen job holds its memory for nothing, a big one most. A batch job expected to reach `keep_gb` (8) or with `keep_core_h` (1) of work in it is kept running: never frozen for a grant, never throttled, first for memory after timed jobs. When it is short, the newest batch job not kept is frozen (and compressed) to make room, never requeued. A thawed job is not frozen again for max(`thaw_min_run_s` 600, `thaw_min_frac` 25% of the time it was frozen) unless free memory is below half the buffer. Chosen by replaying a day of traces with less memory (`tools/kaeq/sim_freeze.py`): the run window was the largest gain at no throughput cost; setting big jobs' forecast growth aside (`keep_reserve_frac`, default 0) or requeueing to make room cost 20-30% of throughput or 35-40 core-h; ordering by memory / time left gained little. CPU (`heavy_boost`): memory-heavy jobs get one step more priority, so they wait less under contention. Without privileges a priority can only be lowered, so only jobs expected to be memory-heavy (their learned size, or `--mem` without history, at least `keep_gb`) start one step up (timed: nice `timed_nice`; batch: nice 19, normal scheduling); the rest start one step down (timed: nice + 1; batch: `SCHED_IDLE`), and a boosted job is moved down after `lease_warm_s` if its learned size says it is light. A job that turns heavy later cannot be raised: that needs the cpu controller delegated (`cpu.weight`, `cpu.idle`) or an `RLIMIT_NICE` above 0. |
| CPU for timed jobs (measured, not reserved) | Jobs' CPU use varies by phase, so nothing is reserved. Every 10 s the daemon reads each job's cores used (`cpu.stat`) and the seconds some / all of its runnable threads waited for a CPU (`cpu.pressure`, which needs no delegated cpu controller). A timed job starts only while the running timed jobs' mean use over `cpu_window_s` (10 min) plus their bursts (max minus mean) pooled as independent (root of the summed squares), plus its own (its owner's finished jobs: median mean use, p90 peak; else `--cpus`), fit in the CPUs jobs may use beside other users' load, and while timed jobs had a thread waiting for a CPU under `timed_wait_start` (2%) of the time. Above `timed_wait_freeze` (5%), the newest batch job is frozen, one per `cpu_freeze_every_s` (10 s), and once below `timed_wait_thaw` (1%) that long, thawed again, oldest first. Each job records the seconds its threads waited (`cpu_wait_s`, `cpu_stall_s`): time contention took from its budgets, shown by `kaeq status`, `kaeq result` and `kaeq usage`. |
| Memory leases (default, `mem_pool=lease`) | Each running job holds a grant, enforced as its scope's `memory.high`; it starts at its `--mem` (scaled by its owner's learned peak/`--mem`). A job is not killed for needing more: once its non-reclaimable memory (anon + shmem + kernel, from `memory.stat`; page cache is reclaimed) comes within `max(lease_margin_mb, lease_margin_frac × grant)` (512 MB, 15%) of its grant, the daemon grants `max(lease_step_gb, lease_step_frac × grant)` (1 GB, 25%) more, or half the grant when far more is free. If nothing is free, the job runs on in the room it still has, and only once it is within `max(lease_freeze_mb, 2 ticks of its measured growth)` (256 MB) of its grant does it wait **frozen** (`cgroup.freeze`): it neither runs nor allocates, so it builds no memory pressure (systemd-oomd kills a scope under sustained pressure, which a job throttled at `memory.high` is). It is thawed when the grant grows. Time frozen does not count towards `--timeout` (which counts active time: wall time minus time frozen), and the freeze is recorded in the database, so a restarted daemon adopts a frozen job as frozen. `memory.high` sits `max(1 GB, lease_backstop_frac × grant)` (10%) above the grant, a backstop for a burst between two daemon ticks. A grant is a limit, not a reservation. Grants grow, and new jobs start, from memory really free beyond the reserve (`MemAvailable`, and `mem_budget_gb`, if set), minus a growth buffer (`lease_buffer_ticks` (3) × the most all jobs together grew within one tick over the last 10 minutes, at least `lease_buffer_gb`, 4 GB), minus the unused grant of jobs younger than `lease_warm_s` (2 min) in full and `lease_hold_frac` (25%) of every other job's unused grant (1 makes grants reservations again), by priority, then oldest job first. If jobs grow into the buffer anyway, those that grew in the last tick are frozen at what they use, lowest priority and newest first; while at least half the buffer is left, the oldest job of highest priority grows on, so peaks take turns instead of being reserved for. While any job waits at its grant, no new job starts. A grant more than `max(lease_release_gb, lease_release_frac × use)` (2 GB, 25%) above use for `lease_release_after_s` (2 min), once the job is past its first `warmup_s` (5 min), is trimmed to use × 1.25 (at least use + 1 GB), so another job can have it. If a job has waited `lease_stall_s` (15 min) and nothing frees (its current stall, or all its time frozen since the last requeue made room for it, so a job thawed and frozen again over and over counts as waiting), one job of no higher priority is requeued with `--mem` raised to what it used: the one furthest past `mem_overrun` (1.5) × its declared `--mem` (a runaway, even the waiting job itself), else the newest other job; a job within its declaration that only waits for other users' memory keeps waiting. `kaeq status` shows each job's grant; `kaeqtop` shows the grants and who waits. The `--mem` overrun kill does not apply to leased jobs. Only batch jobs are frozen or requeued by these rules. Needs the cgroup memory controller (`kaeq doctor`); without it the queue falls back to `measured` below. |
| Other users' RAM | Without leases, admission is measured: a job starts only if `MemAvailable - reserve_mem_gb - what running jobs may still grow into >= its --mem`. A job younger than `warmup_s` (300 s) may grow into its declared `--mem`; after that, into its observed peak × `peak_margin` (1.25), so a later, heavier phase is still covered. With `mem_pool=measured` (the fallback) the queue does not add up worst cases at all: it measures how much its running jobs together have actually grown (their summed RSS once past warm-up, with starts and finishes excluded) and sets aside the largest rise within any hour of the last 24 h × `mem_rise_margin` (1.25), at least the largest single job's headroom, plus what jobs still warming up may need (pooled too: each one's peak drawn from its owner's finished jobs' spread of peak/`--mem`, mean + 2 std over all of them). A new job needs its `--mem` scaled by its owner's learned p95 peak/`--mem` (× 1.2, from 20 finished jobs). The history survives restarts (`~/.kaeq/memrise.<host>.json`); with under an hour of it, the model below is used. With `mem_pool=pooled`, jobs' growth is pooled statistically (`peak` sums every job's worst case): each finished job observed for at least half its run leaves a histogram of how its RSS spent its life relative to its peak, and once an owner has `mem_pool_min_jobs` (5) of them, its running jobs count as random variables. The queue sets aside the mean plus `mem_pool_z` (3) standard deviations of their combined growth, with jobs of one owner correlated as measured (mean Pearson r of concurrent jobs' last 15 min of RSS, shrunk towards the prior `mem_pool_rho`, 0.5) and different owners independent; never less than the largest single job's headroom, never more than the sum. Jobs still warming up, and owners without enough history, count in full. Jobs start one per tick (`starts_per_tick`, every 2 s): each new job shows its memory before more start. If free RAM drops below `emergency_frac` (75%) of the reserve, the newest job is killed and requeued (`preempted`); this backstop applies with leases too. |
| Reserves | `reserve_cpu` and `reserve_mem_gb` default to `reserve_frac` (20%) of threads and RAM. |
| Wrong estimates (without leases) | RSS (summed over the job's cgroup scope, else its session) polled every 2 s; > 1.5x declared (+1 GB) kills the job and requeues it once with `--mem` corrected from the observed peak. |
| Kernel OOM | `oom_score_adj=1000`: our jobs are the victims, not other users' processes. |
| Disk I/O | `ionice -c3`. |
| Scratch disk | Each job gets `$KAEQ_SCRATCH` (also `TMPDIR`) under `scratch_dir` (default `/var/tmp/$USER/kaeq-scratch`), deleted when the job ends, fails, is cancelled or preempted. Admission keeps measured scratch plus the unused part of declared `--disk` under `scratch_gb` (100). A job over 3x its `--disk` (+5 GB) is killed and requeued with a corrected estimate; over budget overall, the largest user is preempted. |
| Hard backstop | If `systemd-run --user` has the memory controller delegated (`kaeq doctor`), each job gets its own scope (with leases: `MemoryHigh` = its grant; without: `MemoryMax=2x`), inside `kaeq.slice` capped at `(1 - reserve_frac)` of RAM by `install-service`. Not required. |
| State on NFS | When `~/.kaeq` is on a network share, the SQLite database lives on local disk (`/var/tmp/$USER/kaeq/queue.db`), is backed up to `~/.kaeq/queue.db.bak` every 5 minutes, and is restored from there if the local copy is lost. Logs stay in `~/.kaeq/jobs/<id>/log`. |
| Fairness | Order: priority, then owners with the fewest running jobs, then age. A head-of-line job waiting > 10 min blocks backfill so big jobs don't starve, except by owners whose recent jobs end quickly (p90 of the last 50 ≤ `backfill_short_s`, 30 min): those still fill the held room, so a big job waits at most about that much longer once its room frees. |

Tune with `kaeq config --set reserve_frac=0.25 --set scratch_gb=150` (read every tick).
Per-job resources in bulk: `kaeq submit --jobs FILE` (JSONL: `cmd`, `name`, `cpus`, `mem`, `disk`, `timeout`, `prio`).
Change the priority of queued jobs: `kaeq prio N [ids] [--owner O] [--tag T]` (higher runs first).
Time accounting: every attempt records its active time, time frozen and how often, and CPU seconds (from its scope's `cpu.stat`); an attempt thrown away (preempted, requeued for memory or disk, retried) adds its active and CPU time to the job's `lost_run_s`/`lost_cpu_s`. `kaeq usage [--owner O] [--tag T] [--since 24h]` sums these per owner (CPU also as a share of the CPUs declared); `kaeq status`, `kaeq result` and failure digests show them per job.
Watch the queue live: `kaeqtop` (text only, fine over SSH): machine CPU/RAM as the scheduler sees them, what the next job waits for, and per owner priority, running jobs, CPU, RAM, memory set aside, progress, rate and ETA.
Jobs get `KAEQ_CPUS`, `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `GOMAXPROCS` = `--cpus`, and the
submitter's `PATH`/`VIRTUAL_ENV`/`PYTHONPATH` (so the right venv is used).

## Many repos and branches

Each submit freezes the caller's tree (`git commit-tree` over HEAD + uncommitted + untracked,
kept alive by `refs/kaeq/<sha>`) and the daemon runs the job in a throwaway `git worktree` of the
submitter's repo, in the same subdirectory. Checkouts or edits after submit cannot change what
runs, and two branches of one repo can run side by side. The worktree is removed when the job
ends; the log stays. Git-ignored inputs are not in a snapshot: share them with `--link PATH`
(symlinked from the original repo). `--live` skips snapshots. Outside git, jobs run live.
The default owner is `repo@branch`; failure digests carry `repo@branch:sha`.
Old `refs/kaeq/*` can be deleted any time once no queued job needs them.

## One daemon, one machine

A POSIX lock on `~/.kaeq/daemon.lock` admits one daemon, even across machines that share an NFS
home: pids are not comparable across hosts or namespaces, but NFS locks are. The daemon pins its
host and database path in `~/.kaeq/config.json`. A client on another machine stops and points
at `KAEQ_SSH=<host>` instead of starting a second queue. Heartbeat (`daemon.<host>.json`), backup
(`queue.<host>.db.bak`) and exit-code files (`jobs/<id>/rc.<host>.<attempt>.<preempts>`) are per
host and per start, so nothing else writing into a shared home can end a job.

## Reporting loop

`kaeq wait` (run in the background) blocks until the owner has a problem event
(failed/timeout/oom/lost) or finished everything, prints one compact digest per failure
(command name, rc, runtime, peak/declared memory, earlier error lines, log tail, log path),
and exits 1/0 (2 = timeout, call again). Successes are never printed individually.
The session fixes the code and runs `kaeq retry [ids]`; it reuses the same command and cwd.
State lives in `~/.kaeq` (SQLite WAL, per-job `log`); the daemon can restart without
losing running jobs (they are re-adopted).

## Limits

- Jobs run as the daemon's user; submitters need access to the same `~/.kaeq` (same account or `KAEQ_HOME`).
- CPU weighting via cgroup `CPUWeight` would need a root-created systemd drop-in delegating `cpu`; `SCHED_IDLE` makes it unnecessary.
- RSS is summed per job session and over-counts shared pages (conservative).
